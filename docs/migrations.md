# Migrations

How to change the database schema without taking the API down. The
three-database scheme and why it exists are in
[ADR-0005](adr/0005-alembic-migrations-and-three-databases.md); this page is
the protocol for writing and landing a migration.

## Why this needs a protocol: migrations run at boot

Render's free tier has no pre-deploy hook, so
[`backend/start.sh`](../backend/start.sh) runs `alembic upgrade head` on
**every boot**, before uvicorn starts
([ADR-0011](adr/0011-backend-hosting-render.md)). Every merge to `main` that
touches `backend/` redeploys, and every cold-start wake reruns it.

So anything that makes `alembic upgrade head` fail is not a failed deploy step —
it is an API that will not start. In particular:

| Mistake | What production does |
| --- | --- |
| Two heads on `main` | `upgrade head` refuses to choose; the API does not boot |
| An applied migration edited after the fact | Nothing — Alembic only reads the revision ID, so the edit never runs and the schema silently disagrees with the code |
| A migration that fails half-way | Boot fails; the schema may be left part-applied (DDL is not transactional for every statement) |
| Models changed with no migration | Boots fine, then queries fail against a stale schema |

The last one is what `make migrate-check` catches. The first is what
`make migrate-heads` catches. The middle two are discipline, below.

## The rules

1. **One head, always.** The revision chain on `main` is linear: every
   migration's `down_revision` is the head that was on `main` when it merged.
   No branches, and no `alembic merge` revisions — a merge revision works, but a
   linear chain is the one a reviewer can read top to bottom.
2. **Never edit a migration production has applied.** Alembic records only
   the revision ID in `alembic_version`; it never notices that the file
   changed. To change something already applied, write a new migration.
   (A migration that is on `main` but never got past boot — the two-heads case
   below — has not been applied, and is the one exception.)
3. **Review every autogenerated file before committing it.** See below.
4. **`make check` passes before the PR opens.** It runs `migrate-heads` and
   `migrate-check` ahead of the test suites, exactly as CI does.

## Writing a migration

```sh
make migration m="add reference to bill"   # autogenerate against your dev DB
# edit the generated file — see the review checklist
make migrate-check                          # applies from scratch, compares to models
make check                                  # the gate
```

`make migration` autogenerates against *your* database, so run `make migrate`
first if it is behind `main`, or the diff will include other people's changes.

### Reviewing an autogenerated diff

Autogenerate compares the models with a database and writes down the
difference. It is a draft, not an answer. Read the whole file and check:

- **Renames.** Autogenerate cannot see them. A renamed column or table comes out
  as `drop_column` + `add_column` (or `drop_table` + `create_table`), which
  **deletes the data**. Replace the pair with `op.alter_column(...,
  new_column_name=...)` or `op.rename_table(...)`.
- **Drops you did not intend.** Any `drop_*` is worth a second look: it often
  means your dev database has something `main` does not, not that the model lost
  it.
- **`NOT NULL` on an existing table.** Adding a non-nullable column with no
  `server_default` fails on any table with rows — production has rows even if
  your dev database does not. Add a default, or add it nullable, backfill, then
  tighten.
- **Missing imports.** Custom column types (fastapi-users' `GUID`, for one) are
  emitted without their import; see `1baee1682c46` for the fix.
- **Enums, constraints, server defaults.** Autogenerate misses some changes to
  these. Compare against the model by hand.
- **Data migrations.** Autogenerate writes schema only. Moving or reshaping
  data is hand-written, in its own migration, with a `downgrade()` that at
  least does not crash.
- **`downgrade()`.** It is never run in CI (ADR-0005 limitations), so make it
  plausible, but the working strategy is forward-fix.
- **The message and filename.** They are the history; make the message say
  what changed, as `make migration m="..."` does.

## Two heads: when two PRs each add a migration

The common way to break rule 1 is innocent: two branches each start from the
same `main` and each add one migration. Each PR has one head and passes CI on
its own. After both merge, `main` has two heads, both pointing at the same
parent, and the next boot fails.

`make migrate-heads` reads `alembic/versions/` (no database needed) and fails
with the heads, their parents and their files. `alembic/env.py` runs the same
check, so CI's migration step and the Render boot log print the same
explanation instead of Alembic's bare "Multiple head revisions are present".

### Fixing it

On your branch, after merging or rebasing `main` in:

1. Run `make migrate-heads`. It lists two heads; one is yours, the other is
   already on `main`.
2. In **your** migration file, set `down_revision` to the other head's
   revision ID, and update the `Revises:` line in its docstring to match.
3. Run `make migrate-check` — your migration now applies on top of the other
   one, and the result must still match the models. If both migrations touch
   the same table, read them together: the order is now fixed.
4. Push a new commit.

If both heads have already reached `main`, the API is not booting: open a PR
that does the same repoint to the migration that merged **last**. It has never
been applied — no boot got past it — so editing it is safe, and the other one
must not be touched because production may already have applied it.
