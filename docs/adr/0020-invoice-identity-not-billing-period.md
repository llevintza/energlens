# 0020. Identify a bill by its invoice number, not its billing period

- **Status:** Accepted
- **Date:** 2026-08-13
- **Deciders:** llevintza
- **Landed in:** PR #67
- **Related:** [ADR-0004](0004-postgresql-as-the-datastore.md),
  [ADR-0005](0005-alembic-migrations-and-three-databases.md), issues #49, #52

## Context

`bills` was unique on `(place_id, utility_type, period_start, period_end)`, and
[`docs/architecture.md`](../architecture.md) called that constraint "what makes
ingestion idempotent". It held for as long as the only bills in the system were one
per month per place, generated by the seed or typed in by hand.

The corpus of thirty real Romanian PPC invoices disproves it. `2024-12-1.pdf` is a
`Stornare` — a reversal — of invoice `24MI 15990831`. It prints the *same* billing
period as `2024-11.pdf`, `01.11.2024–30.11.2024`, with −41 kWh and −27,88 lei. Both
documents are genuine, both belong in the ledger, and the constraint admitted only
one of them: two of the thirty bills could not be inserted at all. The same pattern
repeats with `2024-12-2.pdf`, which reverses `2024-10.pdf` before `2024-12-3.pdf`
re-bills the corrected window.

A billing period was never identity. It is a property of the *consumption*; the
provider's own invoice number is the identity of the *document*. The distinction
did not matter until the system had to hold corrections, and it has to hold them
before the extraction agent (#50) can write to this schema at all.

The constraint could not simply be dropped. `ingest/`'s re-run story rests on it:
the CLI uploads a directory of PDFs, treats a 409 as "already there", and
[`README.md`](../../README.md) promises re-runs skip what is already uploaded.
Removing the constraint without replacing that behaviour would have turned every
re-run into a silent duplicate — the worst kind of regression, because nothing
fails.

## Decision

**We identify a bill by `(place_id, provider_invoice_series, provider_invoice_number)`,
and keep the period rule in application code for bills that carry no invoice number.**

- `uq_bills_place_invoice` replaces `uq_bills_place_period` in the database.
- PostgreSQL treats NULLs in a UNIQUE tuple as distinct, so bills with no invoice
  number are unconstrained by it. That is the desired behaviour for manual entry,
  and it is also why the rule cannot stop there.
- `create_bill` and `update_bill` in
  [`backend/app/routers/bills.py`](../../backend/app/routers/bills.py) answer 409
  on a duplicate invoice number when the incoming bill has one, and otherwise on a
  duplicate `(place, utility type, period)` — the exact old rule, checked against
  every bill at that period regardless of whether *it* carries a number.
- A credit note points at what it reverses through `corrects_bill_id`, a
  self-referential FK that is **`ON DELETE SET NULL`** where every other FK in this
  schema is `CASCADE`.

## Consequences

### What this buys

- The corpus fits. A reversal and the invoice it reverses coexist, and the chain
  between them is recorded rather than inferred from the amounts.
- Ingestion idempotency gets *stronger* where an invoice number exists: re-importing
  the same PDF conflicts even if someone edited its period, which the old constraint
  would have missed.
- The ingest CLI's behaviour is unchanged. It sends no invoice number, so it still
  gets the period rule.
- `data/bills/` becomes a valid target for the extraction agent, which was the
  precondition for the rest of #49.

### What this costs

- **A uniqueness rule now lives in two places** — one constraint in the database, one
  branch in the router. The database alone no longer tells you what a duplicate is,
  and the application check is subject to a race that the constraint is not. The
  race is narrow (two concurrent creates of the same numberless period) and its
  outcome is a duplicate row rather than corruption, so it is accepted rather than
  locked against.
- **The 409 message became load-bearing.** Two different rules produce the same
  status code, so the API returns which one fired and the UI shows the server's text
  instead of its own.
- **`corrects_bill_id` needs an ownership check.** The FK names `bills.id` globally,
  so without a check in the router any signed-in user could link a credit note to a
  stranger's bill id. That check is application-level and tested; a database
  constraint cannot express it, because ownership runs through `places`.
- **`downgrade()` can fail.** Recreating the period constraint is impossible once a
  place holds a reversal and its original. Deliberate: the alternative is deleting
  one of the two rows to make room.

## Limitations

- `provider_invoice_series` is `String(20)` and `provider_invoice_number` is
  `String(50)`. The corpus prints `24MI` / `15990831`; a provider numbering beyond
  that needs a migration.
- Uniqueness is per place, not per user or per provider. Two places holding invoices
  that share a number is legal, and `provider_tax_id` — not the number — is what
  tells `PPC Energie Muntenia S.A.` from `PPC Energie S.A.` across the 2025-03
  handover.
- The number is taken as printed. Nothing normalises whitespace, case, or leading
  zeros, so `15990831` and ` 15990831` would be two bills.
- Only one level of correction is modelled. A credit note that is itself reversed
  forms a chain nothing walks yet, and only self-reference is refused — a longer
  cycle is not detected.

## Alternatives considered

| Option | Why not |
| --- | --- |
| Add `document_type` to the period constraint | Lets one reversal through and blocks the second. `2024-12-2` and `2024-12-3` both correct the same original window. |
| Drop uniqueness entirely, dedupe on the PDF's sha256 | That is #54's `bill_documents`, and it identifies a *file*, not an invoice. The same invoice arrives as a different file whenever it is re-downloaded. |
| Keep the period constraint, store reversals in a separate table | Two tables holding money that has to be summed together. Every query in `services/series.py` would need a UNION, and the epic forbids changing what it computes. |
| Make the invoice number NOT NULL | Manual entry has no invoice number, and neither does anything the CLI has already uploaded. It would make the primary way people add bills impossible. |
| Enforce the fallback with a partial unique index on `(place, period) WHERE provider_invoice_number IS NULL` | Closes the race, but only for numberless-vs-numberless. It cannot see a numberless bill duplicating a numbered one, which is the case that follows once #50 imports invoices alongside hand-typed bills. Worth revisiting if the race is ever observed. |

## Revisit when

- [ ] A provider is onboarded whose invoice numbers repeat within a place, or which
      prints no number at all — the fallback would then be carrying the load it was
      meant to be an exception for.
- [ ] Two concurrent creates are observed producing duplicate numberless bills. The
      partial unique index above is the fix.
- [ ] Correction chains exceed one hop, or a UI needs to walk them — that is when
      `corrects_bill_id` needs an ORM relationship and cycle detection deeper than
      self-reference.
- [ ] `bill_documents` (#54) lands and sha256 dedupe overlaps this rule. Decide then
      which one answers "already imported".

## Migration path

Reversing this means recreating `uq_bills_place_period`, which fails while any place
holds a reversal and its original — the data has to be resolved first, and that is a
product decision, not a schema one. The `downgrade()` in
`backend/alembic/versions/4c3dd9fa0449_*.py` does the mechanical half and will stop
there if the data does not allow it.

Moving *forward* — to sha256 or to a provider-scoped rule — touches the constraint,
`_duplicate_detail` in `backend/app/routers/bills.py`, and the README paragraph
describing re-runs. The ingest CLI does not need to change either way, because it
sends no invoice number and reads only the status code.
